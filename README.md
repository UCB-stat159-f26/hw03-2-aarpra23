# ❀ tennisages ❀

An R package that downloads a tennis player's career matches from [Tennis Abstract](https://www.tennisabstract.com) and plots each match by the player's age and the age gap with the opponent, like the New York Times graphic of Serena Williams's career.

## ❀ Installation ❀

```r
devtools::install_github("UCB-stat159-f26/hw03-2-aarpra23")
library(tennisages)
```

## ❀ Usage ❀

```r
# Serena Williams data and plot
serena = get_career_matches("serena williams")
plot_age_gap(serena)

# Rafael Nadal data and plot
rafa = get_career_matches("Rafael Nadal")
plot_age_gap(rafa)

# invalid players give an error message
get_career_matches("GastonSanchez")
```

Player names can be typed as `"serena williams"`, `"Serena Williams"` or `"SerenaWilliams"`.

## ❀ Functions ❀

### `get_career_matches(player_name)`

Downloads a player's career matches from Tennis Abstract and cleans them into a data frame.

- **Input:** a player's name, e.g. `"serena williams"`, `"Serena Williams"` or `"SerenaWilliams"`
- **Output:** a data frame with one row per match

### `plot_age_gap(career_matches)`

Makes the scatter plot of the player's age against the age gap with each opponent, colored by win or loss.

- **Input:** the data frame from `get_career_matches()`
- **Output:** a ggplot object
- 
## ❀ How it works ❀

- Career files for female players list each opponent's birth date, while files for male players list the opponent's age, so the package checks which format each row uses.
- The career files don't include the player's own birth date, so the package also reads it from the player's Tennis Abstract page (`player.cgi` for men, `wplayer.cgi` for women).

## ❀ Reflections ❀

   The biggest difference between this assignment and the previous one was moving away from code that is specific to one case to one that works for any case. In the previous assignment, I hardcoded Williams's birthdate and wrote scripts that only had to run once on one file. Making the package general highlighted how many assumptions I had built into my code without noticing. Male and female files have different layouts, where the female files provide the opponent's birthdate and calculate the age, while the male files provide the age directly. The player's own birthdates were not in the files at all, so I had to write helper functions that pulled it from their Tennis Abstract pages instead. 
   Writing tests with a mockup JS file taught me the most out of the whole assignment. My `extract_match_array()` function used a regex that I had initially believed to remove everything after the last `]`, but it only removed one character. Every file I had tried ended with `]` so the function cut off the semicolon and seemed to work. My mockup file didn't end in a semicolon, causing the test to fail since the array was being cut off. The real data was hiding a bug which the fake file exposed. I pivoted to find the first `[` and the last `]` by position, which was the same approach I had used in the previous assignment. This really highlighted the efficiency and need for tests as a way to check inputs that I wouldn't have thought of and double check that my code works. The 20 line limit also changed the way I approached writing functions. My cleaning script in the previous assignment was one long code block, where here I split it into multiple, shorter private helper functions. This made things easier to test and fix when something went wrong. 
   Overall, I learned that writing R packages is all about structure. The code has to live in a folder named `R`, tests have to be in `tests/testthat` with a `test-` prefix, roxygen comments generate the `NAMESPACE` and help pages, and `R CMD build` would not work until the DESCRIPTION had been fully and accurately filled out. I had initially though that these rules seemed rather picky, but later realized that they were key to allowing someone else to install the package with one line and make it work.
